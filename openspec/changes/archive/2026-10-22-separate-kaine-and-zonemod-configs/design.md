## 背景

本仓库是 SirPlease/L4D2-Competitive-Rework 的定制分支。当前 `cfg/cfgogl/zonemod/` 标记为 ZoneMod 2.9.1b，并被原生 `zonemod`、`zm1v1`、`zm2v2`、`zm3v3`、`zm1v1nojockey` 和 `zm1v4` 模式引用。当前工作区修改了 `zonemod` 的共享插件、共享设置和武器限制文件；`zonemod4K` 也有本地武器和插件改动，`zm1v4` 同样包含本地改动。这些工作区改动不能在恢复上游文件时丢弃。

上游 SirPlease 仓库的 ZoneMod 2.9.2b 配置已锁定到提交 `3fd5dcb9801d0c401a7b3f2fc7196b71a97b5044`（提交信息为 “Zonemod 2.9.2b”）。现有 `zonemod4K` 是单独的较旧 4K 配置；现有 ZoneMod 3v3、2v2、1v1 目录没有工作区改动，并继承根目录共享配置。

本地改动分类结果：`zonemod` 的 SI 人数限制、`givewpn` 加载、狙击枪参数和武器限制作为当前 4v4 Kaine 基线保留；`zonemod4K` 的本地武器和插件改动作为 Kaine Quad 保留。`zm1v4` 与 `zoneretro` 有独立的未提交修改，不属于本次迁移，保持不变。原生 `zm1v1`、`zm2v2`、`zm3v3` 没有未提交改动，可以直接用锁定的上游版本更新；更新前会先从它们当前的本地配置复制 Kaine 变体。

上游 2.9.2b 的原生共享插件列表引用了本仓库缺少的 `l4d2_weapon_spawn_variety.smx`。该配置所需的插件源码和二进制已从锁定提交一并取得，并按上游 Git blob ID 校验后补入仓库。

## 目标与非目标

**目标：**

- 将当前可玩的 2.9.1b 衍生规则保留为 KaineMod。
- 为原生 ZoneMod 使用上游 2.9.2b 配置，并建立独立的共享文件链。
- 提供 KaineMod 4v4、3v3、2v2、1v1 和 Quad 模式。
- 除明确引用原生 ZoneMod 共享文件的情况外，其他模式维持原有行为；这类引用需确认继续依赖上游原生配置。
- 记录配置来源，确保保留的本地定制可审查。

**非目标：**

- 除保留当前规则和建立模式变体外，不增加其他 KaineMod 玩法改动。
- 不更新无关的 SourceMod 插件、二进制文件、服务器全局设置或地图内容；若锁定的上游配置引用仓库缺少的必需插件，则补齐该插件的上游源码和二进制文件。
- 不重命名或移除现有原生 ZoneMod 模式 ID，也不改变服务器当前默认模式。

## 设计决策

### 1. 保留原生 ZoneMod 的现有 ID 和路径

现有 `zonemod` ID 和目录继续作为原生 ZoneMod 入口，因为 `cfg/server.cfg` 会强制选择该 ID。`zm1v1`、`zm2v2`、`zm3v3` 也继续注册为原生 ZoneMod 变体。原生共享配置替换为上游 2.9.2b，同时保留各变体自己的设置。原生模式名称标明 2.9.2b。

备选方案：重命名原生 ID 并修改 `server.cfg`。不采用，因为这会造成外部兼容性变化，并可能改变服务器启动时使用的模式。

### 2. 恢复上游配置前，先将当前定制配置独立保存为 KaineMod

将当前 `cfg/cfgogl/zonemod/` 工作区状态中确认属于当前玩法的定制内容迁入 KaineMod 专属共享文件。将当前 `zonemod4K` 规则迁为 Kaine Quad。新增 Kaine 4v4、3v3、2v2、1v1 配置目录；这些目录中的玩法专属共享配置、地图变量、插件列表和卸载配置均引用 Kaine 自己的文件。

建议的模式 ID 为 `kainemod`、`kaine3v3`、`kaine2v2`、`kaine1v1` 和 `kaine4K`，显示名称需标明 KaineMod 和人数/类型。只有在仓库引用或预期服务器流程要求兼容时，才保留 `zonemod4K` 作为指向 Kaine Quad 规则的兼容别名。

备选方案：Kaine 变体继续共享原生 ZoneMod 文件，只覆盖已知差异。不采用，因为未来更新原生配置时会悄然改变 KaineMod。

### 3. 逐项甄别本地改动

逐个对照相关文件的工作区版本、仓库基线和上游 2.9.2b。将有意保留的 Kaine 玩法差异迁入 Kaine 专属文件；原生文件恢复为上游版本；无关改动保持原样。重点检查 `zonemod`、`zonemod4K`、`zm1v4`、`matchmodes.txt` 以及其他模式引用的共享文件。不得对整个目录执行无差别还原。

### 4. 添加 Kaine 模式，但不挪用现有原生变体

`zonemod`、`zm1v1`、`zm2v2`、`zm3v3` 继续对应原生 ZoneMod。另行注册 Kaine 模式。Kaine 1v1、2v2、3v3 从现有对应人数模式配置开始，但使用 Kaine 自己的共享配置，并显示独立的 ReadyUp 名称。Quad 从现有 `zonemod4K` 规则开始。Kaine 4v4 从当前定制的 2.9.1b 根配置开始。

### 5. 静态核对配置归属

检查新目录中的每条 `exec`、插件加载、Stripper 路径、地图变量目录和模式卸载引用。Kaine 专属引用必须指向 Kaine 文件；原生引用必须指向 2.9.2b 配置。还需检查 ZoneHunters、`zm1v4`、`zm1v1nojockey` 和其他模式的引用，决定它们继续依赖原生 ZoneMod，还是需要独立快照以保持原行为。

## 风险与权衡

- [共享文件可能让原生更新影响 Kaine 或其他模式] → 为 Kaine 专属依赖建立独立路径，并在修改原生共享文件前审计所有引用。
- [部分工作区改动可能属于其他模式或未完成工作] → 逐项分类差异，无关改动保持不动。
- [Quad 模式基于不同且较旧的配置] → 将它作为独立 Kaine Quad 规则保留，不在拆分时静默改成 2.9.2b 的 4v4 玩法。
- [上游 2.9.2b 可能改变目录结构或插件依赖] → 对比完整的上游 ZoneMod 配置树，只调整必要的仓库集成点，并在实施前记录所需依赖。
- [其他模式引用 ZoneMod 共享配置] → 列出这些引用，并在恢复原生配置后验证其最终行为。

## 迁移计划

1. 盘点所有 ZoneMod 家族配置的工作区差异和仓库基线差异，记录构成 Kaine 玩法的本地改动。
2. 获取并检查上游 ZoneMod 2.9.2b 配置树，逐文件对比本地 2.9.1b。
3. 修改原生路径前，将确认后的当前 Kaine 配置和 Quad 配置复制到 Kaine 专属目录。
4. 添加 Kaine 模式目录及其 `matchmodes.txt` 条目。
5. 将原生 ZoneMod 路径替换为上游 2.9.2b 文件；仅在上游契约有变化时调整原生 1v1、2v2、3v3 变体。
6. 审计所有引用，并静态检查缺失路径、跨家族引用、模式 ID、显示名称和版本标记。
7. 检查完整差异，确认无关工作区修改均保留。
8. 回滚时从变更备份或版本控制恢复本次修改涉及的配置，并且只撤销本次新增的模式条目。

## 待确认事项

- 实施时确认仓库外的服务器脚本是否依赖现有 `zonemod4K` ID；若依赖，则保留为兼容别名。
- 已确定上游仓库来源；实施时仍需锁定具体的 2.9.2b 提交或发行版本，避免迁移输入随上游后续提交变化。
